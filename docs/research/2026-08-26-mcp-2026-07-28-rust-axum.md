# MCP 2026-07-28 与 Rust/Axum 生产接入研究

日期：2026-08-26

## 结论

- 截至本日，MCP 最新稳定协议版本是 **`2026-07-28`**；`/specification/draft` 是持续变化的下一版草案，不进入生产契约。[稳定规范](https://modelcontextprotocol.io/specification/2026-07-28) · [草案 changelog](https://modelcontextprotocol.io/specification/draft/changelog)
- 当前官方 Rust SDK 的最新稳定版本是 **`rmcp 3.1.4`**（2026-08-20 发布）。它实现 `2026-07-28`，但默认的 `ProtocolVersion::LATEST` 仍指向 `2025-11-25`，本项目必须显式选择 `2026-07-28`。[3.1.4 release](https://github.com/modelcontextprotocol/rust-sdk/releases/tag/rmcp-v3.1.4) · [协议常量源码](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.1.4/crates/rmcp/src/model.rs)
- 首版只支持 **`2026-07-28`**。不实现 initialize/session、旧 GET/DELETE stream、粘性路由或第二套旧协议测试；只有出现明确且重要的不兼容目标客户端时，才重新评估旧协议。
- 服务端只有两个网络适配器：REST 与 MCP。二者调用同一个 `OrderApplication`；CLI 是调用 REST 的远程客户端，绝不链接服务端应用类型或直接访问 MongoDB。
- Cognito 与目标 MCP Host 的 client registration、redirect URI、resource binding 必须先完成端到端验证。该验证是 MCP 实施门槛，不得推迟到上线阶段。
- REST、CLI 与未来 `/mcp` 共享部署根地址 `RESOURCE_URI` 作为 canonical protected resource；它们属于同一订单资源与 capability 模型，不为 `/mcp` 增加第二个 audience。

## 2026-07-28 远程 MCP 模型

### 无会话、逐请求协商

`initialize` / `notifications/initialized`、`Mcp-Session-Id`、独立 GET/DELETE 流以及 `Last-Event-ID` 恢复都已从现代协议删除。每个请求在 `_meta` 中携带协议版本和客户端 capabilities；服务端实现 `server/discover`，但业务正确性不依赖连接或 handler 实例的内存状态。[版本兼容](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) · [变更清单](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

订单仍保存在 MongoDB，认证上下文仍来自 bearer token。`rmcp` 的现代 Streamable HTTP 会按请求创建 handler，因此数据库 handle 和 `OrderApplication` 应作为可 clone 的共享依赖注入。

### Streamable HTTP

生产端点是单一 `POST /mcp`。每个 JSON-RPC 请求独立 POST；响应可以是一个 `application/json` 对象，也可以是仅与该请求关联的 `text/event-stream`。[Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

每个 POST 必须满足：

- `MCP-Protocol-Version` 与 body `_meta.io.modelcontextprotocol/protocolVersion` 一致；
- `Mcp-Method` 必须存在；`tools/call`、`resources/read`、`prompts/get` 还必须有 `Mcp-Name`；
- 被工具 schema 的 `x-mcp-header` 标注的参数必须镜像到 `Mcp-Param-*`；
- header 与 body 不一致时返回 HTTP 400 和 JSON-RPC `HeaderMismatch` (`-32020`)。

`rmcp 3.1.4` 可自动发出并校验这些头，不应重写 header parser。[规范要求](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#standard-request-headers) · [rmcp 标准头支持](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.1.4/README.md#standard-http-headers)

### 缓存、MRTR 与 Tasks

- `server/discover`、各类 list 与 `resources/read` 的 complete result 必须带 `ttlMs` 和 `cacheScope`。订单数据使用 `private`；`tools/list` 只有在所有授权用户看到完全相同的工具时才能使用 `public`。[Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)
- 首版工具不需要额外用户输入，因此不主动使用 MRTR。未来若使用，`requestState` 必须被视为不可信输入，只携带完整性受保护的数据或服务端 opaque handle。[MRTR](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#multiple-round-trip-requests)
- 普通订单查询、状态和备注更新不需要 Tasks。首版不声明 Tasks capability，也不持久化 task 状态。[Tasks](https://modelcontextprotocol.io/extensions/tasks/overview)

## OAuth 与生产安全

远程 MCP 会访问用户订单，因此必须启用授权。MCP server 是 OAuth resource server；Cognito 可以继续作为 authorization server，但现有“验证一个 Cognito JWT”不足以形成 MCP 授权互操作面。

必须补齐：

1. 提供 OAuth Protected Resource Metadata，并在 401 `WWW-Authenticate` 中携带 `resource_metadata` 与所需 scope。
2. authorization request 和 token request 都携带 MCP canonical URI 作为 `resource`；服务端验证 token 确实签发给自身资源。
3. 每个 HTTP 请求携带 bearer token；无效或过期 token 返回 401，权限不足返回 403 `insufficient_scope`。
4. 保留 PKCE S256、issuer 校验和 authorization-server metadata 校验；优先使用 Client ID Metadata Document 或预注册客户端。
5. 在实现 MCP 业务工具前，选择至少一个目标 MCP Host，验证 Cognito client registration、redirect URI、resource parameter、token audience 与刷新流程。验证不通过时先调整授权架构，不得降低 token 校验。

规范细节见 [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)、[Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery) 与 [Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)。

当前代码已经按 `client_id + resource audience + scopes` 构造 Principal，并对权限不足返回 `403 insufficient_scope`。MCP 仍缺 `resource_metadata` challenge、Protected Resource Metadata 路由，以及目标 Host 的真实 OAuth 互操作验证；完成这些之前不能暴露 `/mcp`。

Streamable HTTP 还要求校验所有出现的 `Origin`，非法值返回 403，以防 DNS rebinding。`rmcp` 默认只允许 loopback `Host`，却默认关闭 `Origin` allowlist，因此 Fly.io 上必须显式配置公开 host 和允许的 browser origins；Axum 当前的 `AllowOrigin::mirror_request()` 不是该安全校验的替代品。[传输安全要求](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#security--endpoint) · [rmcp 配置源码](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.1.4/crates/rmcp/src/transport/streamable_http_server/tower.rs)

## 应用、CLI 与数据一致性

真实调用关系是：

```text
Browser extension -> REST adapter -> OrderApplication
MCP host          -> MCP adapter  -> OrderApplication
Agent -> Skill -> CLI -> REST adapter -> OrderApplication
```

- `OrderApplication` 是服务端唯一业务规则与 capability 检查模块。
- REST 与 MCP 只负责 transport DTO、认证提取和错误映射。
- CLI 只依赖公开 REST contract；Skill 只负责选择 CLI 命令和解释结果。
- `TenantScopedOrderRepository` 是应用模块内部 seam，生产使用 Mongo adapter，测试使用 in-memory adapter。每个操作必须携带 `UserId`，不存在无租户方法。

浏览器扩展保持 offline-first：localStorage 是扩展的即时工作副本，MongoDB 是跨设备和 Agent 共享的云副本。同步继续采用 `updatedAt` last-write-wins，但所有写入者都必须推进 `updatedAt`：

- 扩展本地修改继续生成 `updatedAt` 并通过现有同步队列上传；
- MCP/CLI 的状态或备注更新由服务端生成 UTC `updatedAt`，不接受 Agent 伪造时间；
- 扩展下一次 pull-and-merge 会接收更新较新的云端订单；
- 测试覆盖 Agent 写入后扩展拉取、扩展较新写入胜出、云端较新写入胜出和相同订单号的跨用户隔离。

这是已有 last-write-wins 模型的扩展，不引入第二个同步系统或 session 状态机。

## SDK 与验证门槛

固定依赖版本，不跟随 `main`：

```toml
rmcp = { version = "=3.1.4", features = ["server", "transport-streamable-http-server"] }
```

服务端的 `supported_protocol_versions()` 只返回 `2026-07-28`。客户端测试显式使用 Discover lifecycle 与 `V_2026_07_28`，不依赖 `LATEST` 名称。[rmcp lifecycle 示例](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.1.4/README.md#client-lifecycle-modes)

CI 固定使用 `rmcp 3.1.4` 官方 workflow 对应的 `@modelcontextprotocol/conformance@0.2.0-alpha.10`，只运行 `2026-07-28` server suite。[rmcp conformance 状态](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.1.4/ROADMAP.md#conformance) · [rmcp conformance workflow](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.1.4/.github/workflows/conformance.yml)

项目级集成测试覆盖：

- request 无 session ID，header/body mismatch 被拒绝，JSON 与 SSE 响应均可处理；
- 缺失、合法、非法 `Origin`，以及 Fly public `Host`；
- Protected Resource Metadata discovery、PKCE/issuer/resource audience 与 scope；
- `cacheScope=private` 不跨授权上下文复用；
- MCP/CLI restricted principal 无法调用创建、删除或批量写入，即使绕过工具或命令发现；
- REST 与 MCP 经同一 `OrderApplication` 得到一致业务结果；CLI 经公开 REST contract 得到等价结果；
- Agent 写入与扩展 offline-first pull-and-merge 的 last-write-wins 行为。
